# FR-01 仓库与库位管理 — 单元测试

---

## 一、什么是单元测试？

**单元测试**只测 **一个类里的业务逻辑**，把数据库、HTTP、Spring 容器都挡在外面。

以 `WarehouseService.create()` 为例：

| 真跑程序时 | 单元测试时 |
| --- | --- |
| Controller 收请求 → Service 判重 → Mapper 查 MySQL | 直接调 `warehouseService.create()` |
| Mapper 真的连数据库 | 用 Mockito **假装** Mapper 的返回值 |
| 要启动 Spring、配数据库 | 不启动容器，毫秒级跑完 |

**测什么、不测什么**：

| 测 | 不测 |
| --- | --- |
| Service 里的 if/else 业务规则 | Controller 的 JSON 格式、HTTP 状态码 |
| 该抛 `BusinessException` 时是否抛对错误码 | 真数据库是否写入成功 |
| 该调 `mapper.insert` 时有没有调 | SQL 语句写得对不对（那是 Mapper 的事） |

记住 **FIRST** 五个词：**快**、**互不干扰**、**可重复**、**结果自动判定**、**与代码同步写**。

## 二、本项目测哪些类？

FR-01 的单元测试集中在 **Service 层**（业务规则都在这里）：

```
src/test/java/com/eurasia/pro_skill/application/
├── WarehouseServiceTest.java           # 仓库
├── WarehouseZoneServiceTest.java       # 库区
└── WarehouseLocationServiceTest.java   # 库位
```

**为什么不测 Controller？**  
Controller 只做「收参数 → 调 Service → 返回 JSON」，几乎没有业务判断。课程要求把精力放在 **Service 核心逻辑** 上。

**为什么不连数据库？**  
连了库就变成「集成测试」，变慢、还要配 H2/MySQL。单元测试用 Mock，只关心「给定 Mapper 返回 X，Service 会不会做 Y」。

## 三、核心工具：JUnit 5 + Mockito

### 3.1 Given-When-Then 结构

每个测试方法按三步写，读起来像自然语言：

```text
Given  准备假数据：when(mapper.getByCode("WH-TEST")).thenReturn(null)
When   执行被测方法：warehouseService.create(input)
Then   断言结果 + 验证调用：assertEquals(...); verify(mapper).insert(...)
```

### 3.2 关键注解

| 注解 | 作用 |
| --- | --- |
| `@ExtendWith(MockitoExtension.class)` | 在测试类上启用 Mockito |
| `@Mock` | 创建「假」的 Mapper，不会真访问数据库 |
| `@InjectMocks` | 把上面的 Mock 自动塞进被测 Service |
| `@Spy` + MapStruct | Converter 用真实实现（`Mappers.getMapper(...)`），保证 Entity↔Domain 转换可信 |
| `@BeforeEach` | 每个用例前重置公共输入（如 `createInput`） |
| `@DisplayName("创建仓库失败：编码已存在")` | 测试报告里显示中文说明 |

### 3.3 测试类骨架

以 `WarehouseServiceTest` 为例：

```java
@ExtendWith(MockitoExtension.class)
@DisplayName("WarehouseService 单元测试")
class WarehouseServiceTest {

    @Mock
    private WarehouseMapper warehouseMapper;
    @Mock
    private WarehouseZoneMapper warehouseZoneMapper;
    @Mock
    private WarehouseLocationMapper warehouseLocationMapper;
    @Spy
    private WarehouseConverter warehouseConverter = Mappers.getMapper(WarehouseConverter.class);
    // ... 其他 Converter 同理

    @InjectMocks
    private WarehouseService warehouseService;

    // 下面写各个 @Test 方法
}
```

### 3.4 常用 Mockito 写法

| 目的 | 代码 |
| --- | --- |
| 假装「查不到」 | `when(mapper.getByCode("X")).thenReturn(null)` |
| 假装「已存在」 | `when(mapper.getByCode("X")).thenReturn(new WarehouseEntity())` |
| insert 后回填 id | `when(mapper.insert(any())).thenAnswer(inv -> { entity.setId(1L); return 1; })` |
| 断言抛业务异常 | `assertThrows(BusinessException.class, () -> service.create(input))` |
| 断言错误码 | `assertEquals("WAREHOUSE_CODE_EXISTS", ex.getCode())` |
| 验证「不该 insert」 | `verify(mapper, never()).insert(any())` |
| 验证「确实 insert 了」 | `verify(mapper).insert(any(WarehouseEntity.class))` |

## 四、必测业务场景（FR-01）

每个场景对应接口文档里的 **业务规则**，写一条 `@Test` 即可。

### 4.1 仓库 `WarehouseService`

| 场景 | 期望 |
| --- | --- |
| 创建成功 | 返回 `id`；`status = ENABLED`；调用了 `insert` |
| 编码重复 | 抛 `BusinessException`，code=`WAREHOUSE_CODE_EXISTS`；**不**调 `insert` |
| 更新成功 | 字段被修改；调用了 `update` |
| 更新时仓库不存在 | `WAREHOUSE_NOT_FOUND` |
| 删除成功（无库区） | 调用了 `delete` |
| 删除有库区 | `WAREHOUSE_HAS_ZONES`；**不**调 `delete` |
| 库位视图 `getTree` | 返回 仓库→库区→库位 三层结构 |
| 库位视图仓库不存在 | `WAREHOUSE_NOT_FOUND` |
| 分页边界 | `current=0` 校正为 1；`pageSize=200` 校正为 100 |

### 4.2 库区 `WarehouseZoneService`

| 场景 | 期望 |
| --- | --- |
| 创建成功 | 默认 `ENABLED` |
| 仓库不存在 | `WAREHOUSE_NOT_FOUND` |
| 编码重复（同仓内） | `ZONE_CODE_EXISTS` |
| 删除有库位 | `ZONE_HAS_LOCATIONS` |

### 4.3 库位 `WarehouseLocationService`

| 场景 | 期望 |
| --- | --- |
| 创建成功 | 默认 `status = AVAILABLE` |
| 编码重复（同区内） | `LOCATION_CODE_EXISTS` |
| 占用库位改状态 | `LOCATION_OCCUPIED` |
| 占用库位删除 | `LOCATION_OCCUPIED` |
| 详情 `getDetail` | 聚合 location + zone + warehouse 三个对象 |

## 五、完整示例：两个对照用例

打开 `WarehouseServiceTest.java`，重点看「成功」和「失败」成对出现：

### 5.1 创建成功

```java
@Test
@DisplayName("创建仓库成功")
void create_success() {
    // Given：编码不存在
    when(warehouseMapper.getByCode("WH-TEST")).thenReturn(null);
    when(warehouseMapper.insert(any(WarehouseEntity.class))).thenAnswer(invocation -> {
        WarehouseEntity entity = invocation.getArgument(0);
        entity.setId(1L);
        return 1;
    });

    // When
    Warehouse result = warehouseService.create(createInput);

    // Then
    assertEquals(1L, result.getId());
    assertEquals("WH-TEST", result.getCode());
    assertEquals(Warehouse.STATUS_ENABLED, result.getStatus());
    verify(warehouseMapper).insert(any(WarehouseEntity.class));
}
```

### 5.2 创建失败：编码已存在

```java
@Test
@DisplayName("创建仓库失败：编码已存在")
void create_codeExists_throws() {
    // Given：编码已存在
    when(warehouseMapper.getByCode("WH-TEST")).thenReturn(new WarehouseEntity());

    // When & Then
    BusinessException ex = assertThrows(BusinessException.class,
            () -> warehouseService.create(createInput));

    assertEquals("WAREHOUSE_CODE_EXISTS", ex.getCode());
    verify(warehouseMapper, never()).insert(any());
}
```

**对比要点**：成功用例 Mock `getByCode` 返回 `null`；失败用例返回非空 Entity，并断言 `never().insert`。

### 5.3 删除保护示例

```java
@Test
@DisplayName("删除仓库失败：存在库区")
void delete_hasZones_throws() {
    when(warehouseMapper.getById(1L)).thenReturn(buildEntity(1L, "WH-TEST"));
    when(warehouseZoneMapper.countByWarehouseId(1L)).thenReturn(2L);

    BusinessException ex = assertThrows(BusinessException.class,
            () -> warehouseService.delete(1L));

    assertEquals("WAREHOUSE_HAS_ZONES", ex.getCode());
    verify(warehouseMapper, never()).delete(anyLong());
}
```

## 九、常见问题

**Q：单元测试通过了，Swagger 里还是报错？**  
A：正常。单元测试不连真数据库，Swagger 测的是完整运行环境。两者互补，不是替代关系。

**Q：`@InjectMocks` 注入的 Service 里 Converter 是 null？**  
A：Converter 要用 `@Spy` + `Mappers.getMapper(...)` 显式创建，不能 `@Mock`（Mock 的转换结果不可信）。

**Q：`verify(mapper).insert(any())` 失败，提示参数不匹配？**  
A：改用 `verify(mapper).insert(any(WarehouseEntity.class))`，或检查 Service 是否真的调了 insert（可能提前抛异常了）。

**Q：测试报 `UnnecessaryStubbingException`？**  
A：某个 `when(...)` 在本用例执行路径里没被用到。删掉多余的 stub，或把只会被部分用例用到的 stub 挪到对应 `@Test` 里。

**Q：怎么给新方法补测试？**  
A：先看 Service 方法里有几个 `if` 分支 → 每个分支至少一条用例 → 成功一条 + 每种 `BusinessException` 一条。
