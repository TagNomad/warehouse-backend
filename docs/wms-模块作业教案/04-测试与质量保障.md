# FR-01 仓库与库位管理 — 单元测试

---

## 一、什么是单元测试？

**单元测试**只测 **一个类里的业务逻辑**，把数据库、HTTP、Spring 容器都挡在外面。

以 `WarehouseService.create()` 为例：


| 真跑程序时                                        | 单元测试时                           |
| -------------------------------------------- | ------------------------------- |
| Controller 收请求 → Service 判重 → Mapper 查 MySQL | 直接调 `warehouseService.create()` |
| Mapper 真的连数据库                                | 用 Mockito **假装** Mapper 的返回值    |
| 要启动 Spring、配数据库                              | 不启动容器，毫秒级跑完                     |


**测什么、不测什么**：


| 测                               | 不测                            |
| ------------------------------- | ----------------------------- |
| Service 里的 if/else 业务规则         | Controller 的 JSON 格式、HTTP 状态码 |
| 该抛 `BusinessException` 时是否抛对错误码 | 真数据库是否写入成功                    |
| 该调 `mapper.insert` 时有没有调        | SQL 语句写得对不对（那是 Mapper 的事）     |


记住 **FIRST** 五个词：**快**、**互不干扰**、**可重复**、**结果自动判定**、**与代码同步写**。

## 二、本项目测哪些类？

FR-01 的单元测试集中在 **Service 层**（业务规则都在这里）：

```
src/test/java/com/eurasia/pro_skill/application/
├── WarehouseServiceTest.java           # 仓库
├── WarehouseZoneServiceTest.java       # 库区
└── WarehouseLocationServiceTest.java   # 库位
```

**为什么不测 Controller？**  
Controller 只做「收参数 → 调 Service → 返回 JSON」，几乎没有业务判断。课程要求把精力放在 **Service 核心逻辑** 上。

**为什么不连数据库？**  
连了库就变成「集成测试」，变慢、还要配 H2/MySQL。单元测试用 Mock，只关心「给定 Mapper 返回 X，Service 会不会做 Y」。

## 三、JUnit 和 Mockito 各管什么？（先分清再写代码）

很多同学混在一起：**JUnit 负责「跑测试、判对错」；Mockito 负责「造假依赖」**。两者配合，但职责不同。

### 3.1 一句话分工


| 工具          | 角色（比喻） | 干什么                                            |
| ----------- | ------ | ---------------------------------------------- |
| **JUnit 5** | 考试系统   | 找到 `@Test` 方法、自动执行、用 `assert`* 判定通过/失败         |
| **Mockito** | 替身演员   | 创建假的 Mapper，用 `when` 规定返回值，用 `verify` 检查有没有被调用 |


```text
JUnit   → 「请执行 create_success，并检查 assert 是否全过」
Mockito → 「Mapper 别连数据库，按我写的剧本返回 null / 设 id」
```

### 3.2 依赖从哪来？

`pom.xml` 里的 `spring-boot-starter-test` 已包含 JUnit 5 和 Mockito，**不用单独安装**。

```text
mvn test
  → Maven Surefire 插件（找测试类）
  → JUnit 5 引擎（跑 @Test）
  → MockitoExtension（处理 @Mock / @InjectMocks）
```

### 3.3 在代码里怎么区分？对照表

打开 `WarehouseServiceTest.java`，看到一行代码先问：**这是 JUnit 的还是 Mockito 的？**


| 代码                                    | 归属                  | 作用                                     |
| ------------------------------------- | ------------------- | -------------------------------------- |
| `@Test`                               | **JUnit**           | 标记「这是一个测试方法，mvn test 时要执行」             |
| `@DisplayName("创建仓库成功")`              | **JUnit**           | 报告里显示中文名，不影响逻辑                         |
| `@BeforeEach void setUp()`            | **JUnit**           | 每个 `@Test` 执行**前**自动跑，准备 `createInput` |
| `@ExtendWith(MockitoExtension.class)` | **JUnit 调 Mockito** | 告诉 JUnit：跑测试前先让 Mockito 建好假对象          |
| `@Mock WarehouseMapper`               | **Mockito**         | 创建假的 Mapper，不连数据库                      |
| `@InjectMocks WarehouseService`       | **Mockito**         | 创建**真的** Service，把假 Mapper 塞进去         |
| `@Spy WarehouseConverter`             | **Mockito**         | Converter 用真实现（MapStruct），不是全假         |
| `when(...).thenReturn(null)`          | **Mockito**         | 登记剧本：调 `getByCode` 时返回什么               |
| `when(...).thenAnswer(...)`           | **Mockito**         | 登记剧本：调 `insert` 时执行什么副作用               |
| `warehouseService.create(...)`        | **你的业务代码**          | 被测方法（真的 `WarehouseService`）            |
| `assertEquals(...)`                   | **JUnit**           | 断言返回值对不对                               |
| `assertThrows(...)`                   | **JUnit**           | 断言是否抛了指定异常                             |
| `verify(mapper).insert(...)`          | **Mockito**         | 断言 Service 有没有调用 insert                |
| `verify(mapper, never()).insert(...)` | **Mockito**         | 断言 Service **没有**调用 insert             |


### 3.4 谁真谁假？（最容易搞混）

```text
@Mock warehouseMapper        → 假的（替身，不连库）
@InjectMocks warehouseService → 真的（被测对象，业务代码原样执行）
@Spy warehouseConverter      → 真的（Entity↔Domain 转换要可信）
```

**不是「又 mock mapper 又 mock service」**，而是：**mock 手下（Mapper），考老板（Service）**。

### 3.5 执行顺序（JUnit 与 Mockito 怎么配合）

跑 `create_success` 时，时间线是：

```text
① JUnit：new WarehouseServiceTest()
② MockitoExtension（JUnit 通过 @ExtendWith 触发）：
     创建 @Mock Mapper、@Spy Converter、@InjectMocks 真 Service
③ JUnit：执行 @BeforeEach setUp() → 准备 createInput
④ JUnit：执行 @Test create_success() 方法体
⑤ Mockito：when(...) 登记剧本（此时还没调 Service）
⑥ 业务代码：warehouseService.create(createInput)  ← 真的 Service 在跑
⑦ Mockito：Service 内部调 mapper 时被拦截，按剧本返回
⑧ JUnit：assertEquals 判定结果
⑨ Mockito：verify 判定 insert 是否被调用
⑩ JUnit：全过 → 绿色 ✅；有一处失败 → 红色 ❌
```

**业务代码里不会写 `create_success()`**，是 JUnit 在 `mvn test` 时自动反射调用的。

## 四、Given-When-Then 与常用写法

每个测试方法按三步写，并分清每步用到的工具：

```text
Given  准备剧本（Mockito）：when(mapper.getByCode("WH-TEST")).thenReturn(null)
When   执行被测方法（业务代码）：warehouseService.create(input)
Then   判结果（JUnit）：assertEquals(...)
       验调用（Mockito）：verify(mapper).insert(...)
```

### 4.1 测试类骨架（带工具标注）

```java
@ExtendWith(MockitoExtension.class)          // JUnit 启用 Mockito
@DisplayName("WarehouseService 单元测试")     // JUnit 报告标题
class WarehouseServiceTest {

    @Mock                                       // Mockito：假 Mapper
    private WarehouseMapper warehouseMapper;

    @Spy                                        // Mockito：真 Converter
    private WarehouseConverter warehouseConverter = Mappers.getMapper(WarehouseConverter.class);

    @InjectMocks                                // Mockito：真 Service
    private WarehouseService warehouseService;

    @BeforeEach                                 // JUnit：每个测试前执行
    void setUp() { /* 准备 createInput */ }

    @Test                                       // JUnit：标记测试方法
    @DisplayName("创建仓库成功")
    void create_success() { /* Given / When / Then */ }
}
```

## 五、零基础精读：`create_success` 完整走读

> 源码：`src/test/java/.../WarehouseServiceTest.java`  
> 被测业务：`src/main/java/.../WarehouseService.java` 的 `create()` 方法

### 5.1 这个用例在测什么？

**场景**：数据库里还没有编码 `WH-TEST` 的仓库，调用 `create()` 应该成功。

**要证明的 4 件事**：


| #   | 业务规则                 | 怎么验证                                                         |
| --- | -------------------- | ------------------------------------------------------------ |
| 1   | 编码不重复时不抛异常           | 方法正常返回，不抛 `BusinessException`                                |
| 2   | 新建仓库默认 `ENABLED`     | `assertEquals(Warehouse.STATUS_ENABLED, result.getStatus())` |
| 3   | insert 后返回带 `id` 的对象 | `assertEquals(1L, result.getId())`                           |
| 4   | 查重通过后必须调 `insert`    | `verify(warehouseMapper).insert(...)`                        |


### 5.2 完整测试代码（分段说明）

```java
@Test                                          // ← JUnit：mvn test 时执行这个方法
@DisplayName("创建仓库成功")                      // ← JUnit：报告里显示中文
void create_success() {

    // ===== Given（Mockito 登记剧本，此时还没调 Service）=====

    // Service 第一步会调 getByCode("WH-TEST")。
    // 剧本：假装数据库里没有这条 → 返回 null → 允许继续创建。
    when(warehouseMapper.getByCode("WH-TEST")).thenReturn(null);

    // Service 后面会调 insert(entity)。
    // 真库 insert 后会有自增 id，假 Mapper 不会自动给。
    // 剧本：insert 被调用时，手动 entity.setId(1L)，模拟数据库分配主键。
    when(warehouseMapper.insert(any(WarehouseEntity.class))).thenAnswer(invocation -> {
        WarehouseEntity entity = invocation.getArgument(0);
        entity.setId(1L);
        return 1;   // 表示影响了 1 行
    });

    // ===== When（执行真的 Service）=====

    // createInput 在 @BeforeEach 里已准备好（code=WH-TEST）。
    // warehouseService 是 @InjectMocks 创建的真对象，里面注入的是假 Mapper。
    Warehouse result = warehouseService.create(createInput);

    // ===== Then（JUnit 断言 + Mockito 验证）=====

    assertNotNull(result);                                    // JUnit
    assertEquals(1L, result.getId());                         // JUnit
    assertEquals("WH-TEST", result.getCode());                // JUnit
    assertEquals(Warehouse.STATUS_ENABLED, result.getStatus()); // JUnit
    verify(warehouseMapper).insert(any(WarehouseEntity.class)); // Mockito
}
```

### 5.3 假 Mapper 为什么有 `getByCode`？要连数据库吗？

**有方法，但不连库。**

Mockito 生成的不是空对象，而是 `WarehouseMapper` 的**替身（代理）**：

```text
真 Mapper：getByCode() → 执行 @Select SQL → 查 MySQL → 返回结果
假 Mapper：getByCode() → Mockito 拦截 → 查 when 剧本 → 直接返回 null
```


| 问题                         | 答案           |
| -------------------------- | ------------ |
| Service 有没有调用 `getByCode`？ | **有**，和真运行一样 |
| 有没有执行 Mapper 里的 SQL？       | **没有**       |
| 要不要连 MySQL？                | **不要**       |


`when(...).thenReturn(null)` 的意思：**「假如有人调这个方法，别去查库，直接按我写的返回。」**

### 5.4 `create()` 内部逐步执行（对照业务代码）

`warehouseService.create(createInput)` 进入 `WarehouseService.create()` 后：

```text
Step 1  warehouseMapper.getByCode("WH-TEST")
        → Mockito 拦截，按剧本返回 null

Step 2  existing == null → 不抛 WAREHOUSE_CODE_EXISTS，继续

Step 3  new WarehouseEntity()，拷贝 input 字段
        → status 设为 ENABLED，时间设为 now()

Step 4  warehouseMapper.insert(entity)
        → Mockito 拦截，thenAnswer 给 entity.setId(1L)

Step 5  warehouseConverter.toDomain(entity)
        → @Spy 真 MapStruct 转换

Step 6  return result → 回到测试方法的 result 变量
```

### 5.5 和「失败用例」成对理解


|            | `create_success`     | `create_codeExists_throws` |
| ---------- | -------------------- | -------------------------- |
| Mockito 剧本 | `getByCode` → `null` | `getByCode` → 有数据          |
| JUnit 期望   | 正常返回                 | `assertThrows` 抛异常         |
| Mockito 验证 | `verify insert` 被调用  | `verify never insert`      |


同一套**真 Service**，两种**假数据库故事**，验证两种业务分支。

### 5.6 亲手验证：框架确实会自动调用

在 `create_success()` 第一行加：

```java
System.out.println(">>> create_success 被 JUnit 调用了");
```

运行：

```bash
./mvnw test -Dtest=WarehouseServiceTest#create_success
```

终端出现这行字，说明你没有手动调，是 **JUnit 在 mvn test 时自动调的**。

## 七、其他示例用例（对照阅读）

### 7.1 创建失败：编码已存在

```java
@Test
@DisplayName("创建仓库失败：编码已存在")
void create_codeExists_throws() {
    when(warehouseMapper.getByCode("WH-TEST")).thenReturn(new WarehouseEntity());  // Mockito 剧本

    BusinessException ex = assertThrows(BusinessException.class,                  // JUnit 断言
            () -> warehouseService.create(createInput));

    assertEquals("WAREHOUSE_CODE_EXISTS", ex.getCode());                          // JUnit 断言
    verify(warehouseMapper, never()).insert(any());                               // Mockito 验证
}
```

### 7.2 删除保护

```java
@Test
@DisplayName("删除仓库失败：存在库区")
void delete_hasZones_throws() {
    when(warehouseMapper.getById(1L)).thenReturn(buildEntity(1L, "WH-TEST"));
    when(warehouseZoneMapper.countByWarehouseId(1L)).thenReturn(2L);

    BusinessException ex = assertThrows(BusinessException.class,
            () -> warehouseService.delete(1L));

    assertEquals("WAREHOUSE_HAS_ZONES", ex.getCode());
    verify(warehouseMapper, never()).delete(anyLong());
}
```

## 十一、常见问题

**Q：JUnit 和 Mockito 是不是一回事？**  
A：不是。JUnit 负责「跑测试 + assert 判对错」；Mockito 负责「造假 Mapper + when 剧本 + verify 验调用」。`spring-boot-starter-test` 里两个都有。

**Q：`@Test` 是谁调用的？**  
A：JUnit。你执行 `mvn test` 时，Surefire 扫描带 `@Test` 的方法并自动反射调用，业务代码里不会出现 `create_success()` 的调用。

**Q：假 Mapper 有 `getByCode` 方法，真的调用了吗？要连数据库吗？**  
A：Service **会真调**这个方法，但 Mockito 拦截后按 `when` 返回，**不执行 SQL、不连库**。

**Q：Service 也是 Mock 的吗？**  
A：不是。`@InjectMocks warehouseService` 是**真的** `WarehouseService`，只有 `@Mock` 标注的 Mapper 是假的。

**Q：单元测试通过了，Swagger 里还是报错？**  
A：正常。单元测试不连真库；Swagger 测完整运行环境。两者互补。

**Q：`verify` 和 `assertEquals` 有什么区别？**  
A：`assertEquals` 是 **JUnit**，检查返回值对不对；`verify` 是 **Mockito**，检查 Service 有没有调用 Mapper 的某个方法。

**Q：怎么给新方法补测试？**  
A：数 Service 里有几个 `if` 分支 → 每个分支一条用例 → Given 用 Mockito 写剧本，Then 用 JUnit + verify 验证。
