# 综合能力实训 · 备课教案

课堂案例是这个 WMS。学生自己的大作业是另外 15 个选题，验收标准和这里对齐，不要在本仓库里做那 15 个题。

这份教案按七个部分写。第一部分没有改良版。第二到第七部分各一个分支、各一个改良版。后一部分只用前一部分已经跑通的结果。

## 教法

每一块都按这四步，不要先把正确实现交给学生：

1. 讲清不这么设计的漏洞。
2. 项目里先留着这个错，按下面的操作就能复现。
3. 学生自己查：日志、库、页面。TraceId 从第六部分才用来串一次请求。
4. 学生自己改。同一操作不再出错。

代码里同时留缺陷路径和修复路径。能用开关的写在 `application.yaml` 的 `app.lesson` 下，部分分支默认走有问题的一侧，改良版把这一部分里的开关拨到修好的一侧。唯一索引、按库位库存这种不能再关掉的，用改良版上的新迁移。第六部分排错时，把对应开关拨回缺陷路径。

开关都写在 `application.yaml` 的 `app.lesson` 下。库上的约束（唯一索引、乐观锁条件）用前后两次迁移或两次提交演示，不靠开关把已经加上的唯一索引再关掉。

## 本分支留下什么

留下能跑的基础，第 10 周用来接新内容：

- 注册登录、JWT、用户 CRUD
- 仓库–库区–库位，Flyway V1–V6
- 演示账号 `admin` / `Admin@123`，仓库 `WH-001`（华东原料仓），库位 `A-01-01`、`A-01-02`、`B-01-01`
- 单测、`api-contract/http`
- 第一部分的 Compose 基座：MySQL、Adminer、应用容器。数据库主机的缺陷路径在 `docker-compose.localhost.yml`
- 分层约定：`layered-architecture.md`

上学期的用户 CRUD 讲义、FR-01 作业教案、Postman 性能集合、个人介绍材料，已从本分支删除。那些内容不再当新课讲。

## 不做

盘点、FIFO、移库、复杂报表。异步不用 RabbitMQ，也不用 Redis Pub/Sub，用 Stream。Zipkin 只演示。学生不自建告警，不手画全套 Grafana 仪表盘。Nginx 只做反代，不算业务。

## 第一部分 从头讲 Docker（第 10 周）

6 课时。周一 1–2 节讲 Docker，并只启动 MySQL 和 Adminer。周三 1–4 节把应用加进同一份 Compose，读 Dockerfile，确认能登录。课堂上用浏览器打开 [第一部分-讲义.html](./第一部分-讲义.html)。先用 GitHub Desktop 克隆课堂仓库，再按页面把项目跑起来。项目跑起来之后做随堂测验：在自己的 Gitee 仓库新建分支、提交、推送，并在网页上创建 Pull Request、合并。不讲本地 merge 和 rebase。时间安排见 [第一部分-上课教案.md](./第一部分-上课教案.md)。TraceId 不在这周讲。周三最后接上前端仓库 `warehouse-frontend`（分支名和后端相同），用页面登录、展开库区库位。

仓库里的 `docker-compose.dev.yml` 是教师事先写好的，上学期没有当课讲。这周按新内容讲：镜像、容器、Compose、端口、数据卷，以及容器里的 `localhost` 指的是谁。后面的 Redis、MinIO、Nginx、Linux 都往这一份文件上加。

### 内容

两件事，按这个顺序：

1. 用 Compose 启动 MySQL 和 Adminer。Adminer 自己也在容器里，服务器填 `localhost` 会连不上，改成服务名 `mysql` 才能看见表。
2. 把应用容器加进同一份 Compose。主机名直接用服务名 `mysql`，周一已经用 Adminer 演示过写成 `localhost` 会连到自己。构建完成后 `/actuator/health` 为 UP，可以登录。

### 具体设计

**MySQL 和 Adminer。** 周一只启动这两个服务：`docker compose -f docker-compose.dev.yml up -d mysql adminer`。先讲镜像、容器、Compose、端口映射和数据卷，文件由教师写好，学生读并自己执行。

漏洞：Adminer 跑在容器里。登录页的服务器填 `localhost` 时，它找的是自己，MySQL 在旁边那个容器。

复现：打开 `http://localhost:8081`，系统 MySQL，服务器 `localhost`，用户 `root`，密码 `root`，库 `pro_skill`。登录失败。`pro-skill-mysql` 此时是 healthy。

学生查：`docker compose ps`，以及页面上的服务器栏。Compose 里 `ADMINER_DEFAULT_SERVER` 写的是 `mysql`。

学生改：服务器改成 `mysql`。能看见 `tb_user` 和 `warehouse`。再填回 `localhost` 又失败。

**应用的数据库主机名。** 周三把应用加进来，直接用服务名 `mysql`。漏洞周一已经用 Adminer 复现过：容器里的 `localhost` 是容器自己。这节不再让应用先连不上。`docker-compose.localhost.yml` 留在仓库里，第 15 周排错时再叠上去。

课堂上执行：

```bash
docker compose -f docker-compose.dev.yml up -d --build app
```

`http://localhost:8080/actuator/health` 返回 UP。浏览器访问的 `localhost:8080` 是端口映射。应用在容器里面连数据库用的是 `mysql`。这两句分开讲。

日志里的空中括号这周不讲。TraceId 是什么、解决什么、怎么实现，放到第六部分。代码可以先留在仓库里，开关保持 `off`。

分组在周一完成。每组确定自己大作业的选题，并指定谁负责后面作业二的哪一个模块。课堂案例仍全组一起跟着做。

作业一在这周布置。作业一只要求项目能启动、Compose 起 MySQL、登录可用，不要求学生这周就交应用镜像。课堂案例自己的基座要在这周跑通。

## 第二部分 货品与入库（第 11 周整周）

6 课时。周一先复习分层和 Swagger，再做货品。周三讲库存记在哪、入库怎样完成。学生讲义是 [第二部分-讲义.html](./第二部分-讲义.html)，「第二部分」和「第二部分改良版」是同一份，上课按 [第二部分-上课教案.md](./第二部分-上课教案.md)。两个分支 Java 代码相同，改良版只改两个开关的值：`sku-code-check` 从 `off` 到 `on`，`inbound-stock` 从 `sku` 到 `location`。这一周结束时只合并这一次。前端「第二部分」分支有货品页和入库页，同一个按钮在两个后端分支上返回不同（讲义第 16 节）。

### 周一 · 货品

漏洞：编码没有唯一约束时，两条货品可以都叫 `SKU-001`。按编码找货品时 `LIMIT 1` 只拿第一行，另一行永远进不了货。

先留的错：`sku-code-check=off`。`POST /skus` 不查重，`code` 上也没有唯一索引。

复现：连建两次 `{ "code": "SKU-001", "name": "轴承", "unit": "个" }`。两次都是 200，`sku` 里出现两行相同编码。再给入库单加一行 `SKU-001`，行上 `skuId` 是 1。

学生查：`sku` 表按 `code` 分组计数；对照 `V3` 的唯一键和 `WarehouseService.create` 插入前的查询。

改良版：`sku-code-check=on`。插入前 `getByCode`，已存在就 `SKU_CODE_DUPLICATED`。并发时两边都查到「没有」的情况，靠第三部分带来的 `V8` 唯一索引兜底。进第三部分之前把重复行删到只剩一行，否则 `V8` 执行失败。

### 周三 · 库存和入库

漏洞：数量只写在货品的一个总数上，两个库位答不出各自有多少，第三部分按库位出库时无从减起。

先留的错：`inbound-stock=sku`。完成时把行上的数量加进 `sku.on_hand`，行上的 `location_id` 没有传下去。

复现：`SKU-003` 进 `A-01-01` 数量 10，再进 `A-01-02` 数量 8。两次完成都是 200、`COMPLETED`，`on_hand` 是 18，`inventory` 没有数据。

学生查：`inbound_order_line.location_id` 有值，`sku.on_hand` 只有一个数；`InboundService.complete` 里只传了货品主键和数量。

改良版：`inbound-stock=location`。表 `inventory` 按货品 + 库位各一行，列有 `quantity` 和 `version`。两个库位是两行，10 和 8；同一个格子再进 5，还是一行，15，`version` 1。加数量和改状态在两个分支上都是同一个事务。事务边界的漏洞放在第三部分（`inbound-fail-before-status`）。

接口：`GET /skus`，`POST /skus`，`POST /inbound-orders`，`POST /inbound-orders/{id}/lines`，`POST /inbound-orders/{id}/complete`。

## 第三部分 出库与并发（第 12 周、第 13 周）

12 课时。第 12 周做出库和超卖。第 13 周做状态机、乐观锁、事务边界。学生讲义是 [第三部分-讲义.html](./第三部分-讲义.html)，「第三部分」和「第三部分改良版」是同一份。两个分支 Java 代码相同，改良版改的是四个开关的值：`outbound-check`、`optimistic-lock` 从 `off` 到 `on`，`order-state` 从 `open` 到 `enforced`，`flow-after-commit` 从 `off` 到 `on`。对应四块：剩余不足拒绝、已完成的单不能改行、更新带上 version、流水和入库状态同一次提交。这一部分不讲 TraceId。日志里先看「读到数量」和「把数量改成」这两句，编号放到第六部分。前端「第三部分」分支加了出库页，能改行数量、勾选几张单同时完成（讲义第 18 节）。

### 出库

出库表和入库对称：`outbound_order`、`outbound_order_line`。完成接口 `POST /outbound-orders/{id}/complete`。先用第二部分把 `A-01-01` 的 `SKU-001` 做成 10。

漏洞：不看剩余就减。`app.lesson.outbound-check=off`。出 15，该行变成 -5，单据仍是 `COMPLETED`。

学生查：`inventory` 里的负数行。

改良版：`outbound-check=on`。剩余不足返回 `INSUFFICIENT_STOCK`，数量保持 10。这只挡住单次扣穿。

两张单各出 1、库存只剩 1 时，两边都读到 1。`optimistic-lock` 这一部分先保持 `off`，更新是 `where id = ?`。两次都可以成功。本周只确认两次都读到了旧数量。

### 状态机

漏洞：`COMPLETED` 之后仍允许改行数量。账面已经按原数量减过，单据却变成另一个数。

先留的错：`app.lesson.order-state=open`。`PATCH /outbound-orders/{id}/lines/{lineId}` 不看状态。

学生查：单据行数量和 `inventory.quantity` 的差。

改良版：`order-state=enforced`。不是 `DRAFT` 就拒绝，错误码 `ORDER_NOT_EDITABLE`。

### 乐观锁

漏洞：两个事务都读到剩余 1，都提交成功。`@Transactional` 挡不住这件事。

先留的错：`optimistic-lock=off`。更新不带 version。

学生查：两次更新的影响行数都是 1。

改良版：`optimistic-lock=on`。`set quantity = ?, version = version + 1 where id = ? and version = ?`。影响行数为 0 的那一次返回 `STOCK_CONFLICT`。失败的一路直接拒绝，课上不做自动重试。

### 事务边界

漏洞：主事务还可能回滚时，流水已经用另一个事务提交。

先留的错：`flow-after-commit=off`。流水服务是 `REQUIRES_NEW`。把 `inbound-fail-before-status` 设成 `true` 再完成入库。单据没有变成 `COMPLETED`，`stock_flow` 里已经有这个单号。

学生查：没有完成的入库单，却有流水。

改良版：`flow-after-commit=on`。流水和加库存、改状态在同一个事务里。失败开关打开时，单和流水都不留。

## 第四部分 Redis 缓存（第 14 周，接第 15 周周一全天）

14 课时。第 14 周讲缓存、锁和防重复提交。第 15 周周一全天讲异步消息。学生讲义是 [第四部分-讲义.html](./第四部分-讲义.html)，「第四部分」和「第四部分改良版」是同一份，上课按 [第四部分-上课教案.md](./第四部分-上课教案.md)。两个分支 Java 代码相同，改良版改的是五个开关的值。本机跑时 Redis 主机是 `localhost`，Compose 里是服务名 `redis`。

### 缓存

键：`inv:{skuId}:{locationId}`。`GET /inventories?skuId=&locationId=` 未命中时查库并写入。

先留的错：`cache-evict=off`。出库、入库只改 `inventory`，不删这个键。

复现：先查询让缓存写入 10，再出库 3。接口仍返回 10，库里已是 7。

改良版：`cache-evict=on`。事务提交后删除对应键，再查询返回 7。删而不改，提交后才删。

### 锁

先留的错：`stock-lock=after-check`。先读数量、判断够了才 `SET lock:inv:{skuId}:{locationId} NX PX 30000`，写完马上放。两个请求都读到 7，后写的一张被乐观锁拦下，库存够也返回 `STOCK_CONFLICT`。

改良版：`stock-lock=sku-location`。`complete` 不开事务，先按排好序的格子拿锁，再用 `TransactionTemplate` 开事务读和写，提交后按值删锁。锁在事务里面拿不行：MySQL 可重复读下，事务第一次查询就定下快照，等到锁也读到旧数。第三部分的 version 条件仍保留。

### 防重复提交

先留的错：`submit-once=off`。加出库行时不看请求头 `Idempotency-Key`，同一个请求发两次加两行。

改良版：`submit-once=on`。`SET idem:outbound-line:{key} 单号 NX PX 一天`，写不进去就原样返回；插入回滚时删键。

### 异步

Redis Stream `wms:inbound:completed`，消息字段 `orderNo`、`skuId`、`locationId`、`quantity`。消费组 `notice`，消费者每秒 `XREADGROUP`，写一行 `inbound_notice` 后 `XACK`。不用 Pub/Sub，不用 RabbitMQ。

先留的错：`publish-after-commit=off`，入库还在事务中就 XADD，入库回滚了通知照样写出。`consume-once=off`，写完通知、XACK 前失败（演示开关 `consume-fail-before-ack=true`），重投后同一个 `msg_id` 写两行。

改良版：`publish-after-commit=on`，`afterCommit` 里再 XADD。`consume-once=on`，处理前 `SET inbound:consumed:{msgId} NX`，重投时只确认不再写。

## 第五部分 文件（第 15 周周二全天）

6 课时。学生讲义是 [第五部分-讲义.html](./第五部分-讲义.html)，「第五部分」和「第五部分改良版」是同一份，上课按 [第五部分-上课教案.md](./第五部分-上课教案.md)。只做入库单附件：`POST /inbound-orders/{orderId}/attachments` 上传，`GET /inbound-orders/{orderId}/attachments/{attachmentId}` 下载。两个分支 Java 代码相同，改良版改的是两个开关的值。这一部分应用跑在容器里。MinIO 用社区构建 `pgsty/minio`（官方镜像已拉不到），数据放在数据卷里。

### 文件放在哪

先留的错：`file-store=local`。文件写进应用容器的 `/app/data/attachments/{orderNo}/`，`inbound_attachment.file_path` 存绝对路径。

复现：上传后能下载。`docker compose up -d --force-recreate app` 重建应用容器，`/app/data` 没了，下载返回 `FILE_NOT_FOUND`，表里的路径还在。

改良版：`file-store=minio`。内容放进桶 `wms`，key 为 `inbound/{orderNo}/{存放名}`，表里只存 key，不存本机路径，也不存带主机的地址。重建应用容器后照样下载。

### 文件叫什么

先留的错：`file-key=filename`。用页面传来的文件名存放。同一张单两个 `note.txt` 互相覆盖，1 号下载到第二个；文件名 `../../escape.txt` 写到 `/app/data`。

改良版：`file-key=unique`。存放名是 UUID + 扩展名，原名只写进 `file_name`，下载时由 `Content-Disposition` 还给浏览器。

## 第六部分 排错与监控（第 15 周周三至周五）

16 课时。学生讲义是 [第六部分-讲义.html](./第六部分-讲义.html)，「第六部分」和「第六部分改良版」是同一份。改良版只改代码：打开 TraceId、列表按页返回、记下出库耗时和拒绝次数。TraceId 从这一部分才讲。作业二的缺陷记录在这三天里写完。作业三在周三布置。

### TraceId

是什么：这一次 HTTP 请求的编号。同一次完成里的「读到数量」和「把数量改成」带着同一个号。

解决什么：两张出库单几乎同时完成，四行日志穿在一起。没有这个号，圈不出哪一次读到了旧数量。

怎么实现：不在 Controller 里。

1. `observability/TraceIdFilter.java`。开关打开时读请求头 `X-Trace-Id`，没有就生成 UUID，放进 MDC，并写回响应头。请求结束清掉这个键。
2. `application.yaml` 的日志格式 `[%X{traceId}]`。`app.lesson.trace-id` 在前面的部分保持 `off`，括号是空的。
3. `docker-compose.dev.yml` 的 `APP_LESSON_TRACE_ID`。改开关只重建应用容器。

然后把第三部分的乐观锁、第四部分的删缓存和消费幂等拨回缺陷路径。学生用这个号把一次请求、库和 Redis 串起来，再拨回修复路径。

### 慢查询

先留的错：`inventory-query=full`。`GET /inventories/list` 不带 `LIMIT`，带了 `page` 和 `size` 也返回全表。

学生查：`EXPLAIN` 或这次查询的耗时。

改良版：`inventory-query=page`。列表按页返回。`(sku_id, location_id)` 唯一键继续留着。

### Prometheus

先留的错：`metrics=off`。Actuator 只暴露 `health` 和 `info`。出库被拒绝时不计次数。

改良版：`metrics=on`。计时 `wms.outbound.complete`，计数 `wms.outbound.rejected`。端点加上 `prometheus`。Grafana 用已经配好的面板，学生要能指出出库耗时和拒绝次数。不从空白面板画起，不做告警。

## 第七部分 部署（第 16 周周一至周二）

14 课时。把 Compose、Nginx、Linux 接在这两天里讲完。镜像和「localhost 连不上 MySQL」已经在第一部分做过，这里不再新讲 Dockerfile。

### 收进同一份 Compose

漏洞：Redis 或 MinIO 的地址在容器里写成 `localhost`。应用容器去连自己。

学生查：`docker ps` 里 Redis、MinIO 是 Up，应用日志里的主机名是 `localhost`。

学生改：改回服务名 `redis`、`minio`，仍用第一部分的 `docker-compose.dev.yml`。

### Nginx

Nginx 加进同一份 Compose。`/` 给页面，`/api` 转到后端。页面不再直连 `8080`。

### Linux

本机能开，是因为开发机有本机端口和本机 Docker。拷到 Linux 后，这些前提没有了。

学生改：数据库、Redis、MinIO、应用端口、密码都从 `.env` 读取。JDBC 主机保持服务名 `mysql`。开发机和 Linux 用同一份 Compose，只允许 `.env` 里的端口和密码不同。周二下课前冻结功能。
