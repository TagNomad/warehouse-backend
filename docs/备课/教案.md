# 综合能力实训 · 备课教案

课堂案例是这个 WMS。学生自己的大作业是另外 15 个选题，验收标准和这里对齐，不要在本仓库里做那 15 个题。

这份教案按新内容分块。同一天上午的 1–4 节写成同一部分；上午和下午仍然分开。周次只标在每一块标题上，用来对课表。后一块只用前一块已经跑通的结果。

## 教法

每一块都按这四步，不要先把正确实现交给学生：

1. 讲清不这么设计的漏洞。
2. 项目里先留着这个错，按下面的操作就能复现。
3. 学生自己查：日志、库、页面、TraceId。
4. 学生自己改。同一操作不再出错。

代码里同时留缺陷路径和修复路径，用配置开关切换，默认在讲这一块时走缺陷路径。学生改完后，后面的课默认走修复路径，开关仍能拨回去。第 15 周周二排错时，就把对应开关拨回缺陷路径。

开关都写在 `application.yaml` 的 `app.lesson` 下。库上的约束（唯一索引、乐观锁条件）用前后两次迁移或两次提交演示，不靠开关把已经加上的唯一索引再关掉。

## 不做

盘点、FIFO、移库、复杂报表。异步不用 RabbitMQ，也不用 Redis Pub/Sub，用 Stream。Zipkin 只演示。学生不自建告警，不手画全套 Grafana 仪表盘。Nginx 只做反代，不算业务。

## 第一部分 从头讲 Docker（第 10 周）

6 课时。周一 1–2 节讲 Docker，并只启动 MySQL 和 Adminer。周三 1–4 节把应用加进同一份 Compose，读 Dockerfile，确认能登录。课堂上用浏览器打开 [第一部分-讲义.html](./第一部分-讲义.html)。先用 GitHub Desktop 克隆课堂仓库，再按页面把项目跑起来。项目跑起来之后做随堂测验：在自己的 Gitee 仓库新建分支、提交、推送，并在网页上创建 Pull Request、合并。不讲本地 merge 和 rebase。时间安排见 [第一部分-上课教案.md](./第一部分-上课教案.md)。TraceId 不在这周讲。

仓库里的 `docker-compose.dev.yml` 是教师事先写好的，上学期没有当课讲。这周按新内容讲：镜像、容器、Compose、端口、数据卷，以及容器里的 `localhost` 指的是谁。后面的 Redis、MinIO、Nginx、Linux 都往这一份文件上加。

### 内容

两件事，按这个顺序：

1. 用 Compose 启动 MySQL 和 Adminer。Adminer 自己也在容器里，服务器填 `localhost` 会连不上，改成服务名 `mysql` 才能看见表。
2. 把应用容器加进同一份 Compose。主机名直接用服务名 `mysql`，周一已经用 Adminer 演示过写成 `localhost` 会连到自己。构建完成后 `/actuator/health` 为 UP，可以登录。

### 具体设计

**MySQL 和 Adminer。** 周一只启动这两个服务：`docker compose -f docker-compose.dev.yml up -d mysql adminer`。先讲镜像、容器、Compose、端口映射和数据卷，文件由教师写好，学生读并自己执行。

漏洞：Adminer 跑在容器里。登录页的服务器填 `localhost` 时，它找的是自己，MySQL 在旁边那个容器。

复现：打开 `http://localhost:8081`，系统 MySQL，服务器 `localhost`，用户 `root`，密码 `root`，库 `pro_skill`。登录失败。`pro-skill-mysql` 此时是 healthy。

学生查：`docker compose ps`，以及页面上的服务器栏。Compose 里 `ADMINER_DEFAULT_SERVER` 写的是 `mysql`。

学生改：服务器改成 `mysql`。能看见 `tb_user` 和 `warehouse`。再填回 `localhost` 又失败。

**应用的数据库主机名。** 周三把应用加进来，直接用服务名 `mysql`。漏洞周一已经用 Adminer 复现过：容器里的 `localhost` 是容器自己。这节不再让应用先连不上。`docker-compose.localhost.yml` 留在仓库里，第 15 周排错时再叠上去。

课堂上执行：

```bash
docker compose -f docker-compose.dev.yml up -d --build app
```

`http://localhost:8080/actuator/health` 返回 UP。浏览器访问的 `localhost:8080` 是端口映射。应用在容器里面连数据库用的是 `mysql`。这两句分开讲。

日志里的空中括号这周不讲。TraceId 的是什么、解决什么、怎么实现，放在第四部分，两张出库单同时完成的时候讲。代码先留在仓库里，开关保持 `off`。

分组在周一完成。每组确定自己大作业的选题，并指定谁负责后面作业二的哪一个模块。课堂案例仍全组一起跟着做。

作业一在这周布置。作业一只要求项目能启动、Compose 起 MySQL、登录可用，不要求学生这周就交应用镜像。课堂案例自己的基座要在这周跑通。

## 第二部分 先看清代码，再用 Swagger，然后做货品 SKU（第 11 周周一 1–2 节）

2 课时。依赖第一部分：Compose 里的应用已经能连上 MySQL，并且能登录。课堂上打开 [第二部分-讲义.html](./第二部分-讲义.html)。时间安排见 [第二部分-上课教案.md](./第二部分-上课教案.md)。

课前货品表、初始数据和 `/skus` 已经在项目里。这节不重讲登录。按讲义顺着一次创建看数据流。具体类可以用 DeepSeek 或 Kimi 按讲义中的要求生成，再对照仓库里的文件。Dockerfile 不放在这里，它在第 10 周周三讲，讲义在第一部分。

### 复习：一次请求经过哪些层

用登录这一条讲完，不改代码。

`POST /auth/login` 从 `AuthController` 进来，进 `AuthService`，再由 `UserMapper` 读 `tb_user`，通过后签发 JWT。仓库、库区、库位是同一套切法：`controller` 接请求，`application` 写业务，`domain` 是业务对象，`entity` 对表，`mapper` 写 SQL，`converter` 在 domain 和 entity 之间转。

学生要能在仓库里指出这六个包，并说出登录为什么不直接在 Controller 里写 SQL。

### 复习：Swagger

打开 `http://localhost:8080/swagger-ui.html`。

1. 展开 `POST /auth/login`，Try it out，账号 `admin`，密码 `Admin@123`，Execute。应看到 200，响应里有 `token`、`username` 是 `admin`、`role` 是 `ADMIN`。
2. 复制 `token`，点右上角 Authorize，只贴 token，不加 `Bearer`。
3. 再调一个带锁的接口，例如 `GET /warehouses/list`。没授权时是 401，授权后能看到 `WH-001`。

登录接口没有锁。用户、仓库、库区、库位有锁。后面新增的货品接口也要能在这个页面上试。

### 内容

货品主数据。只做编码、名称、单位。不做多规格、不做批次。复习结束才进入下面的缺陷。

### 具体设计

漏洞：编码没有唯一约束时，两条货品可以都叫 `SKU-001`。入库、出库无法知道扣的是哪一条。

课堂上已有的第一版：Flyway `V7` 新建 `sku` 并写入 `SKU-001` 轴承、`SKU-002` 内六角螺栓。`code` 没有唯一索引。`POST /skus` 直接插入，不查重。讲义先讲这一次创建的数据流，不提前说第二次会怎样。

复现：第一版跑起来之后，Swagger 连建两次 `{ "code": "SKU-001", "name": "轴承", "unit": "个" }`。Adminer 里 `sku` 出现两行相同编码。问学生这两行算不算同一种货。

学生查：对照 `V3` 仓库表的 `UNIQUE KEY`，以及 `WarehouseService.create` 插入前的查重。再看自己刚写的 `V7` 和 `SkuService.create`。

学生改：新迁移给 `code` 加唯一索引。第二次创建返回业务错误，例如 `SKU_CODE_DUPLICATED`。库里已有的重复数据要先删掉，迁移才能通过。这一步用提交前后对比，不用开关把唯一索引再关掉。

接口：

- `POST /skus`
- `GET /skus`

作业二在这周布置。作业一在周三截止，核心表初稿至少要有货品，库存和入库表在当天后两节补上。

## 第三部分 库存记在哪，入库完成怎样加数量（第 11 周周三 1–4 节）

4 课时，周三上午一次讲完。依赖第二部分改良版：货品编码已经唯一，库位 `A-01-01`、`A-01-02` 已在。

### 库存记在哪

数量若只写在货品的一个总数上，同一货品放到两个库位时，账面只剩一个合计数，答不出每个格子有多少。

这一支先把数量加在 `sku.on_hand`。完成入库时把行上的数量加进这个总数。

复现：`SKU-001` 入库到 `A-01-01` 数量 10，再到 `A-01-02` 数量 8。`on_hand` 变成 18。问 `A-01-01` 现在有多少，表上答不出来。

### 入库完成

状态只做 `DRAFT` 和 `COMPLETED`。附件留到第十部分。

加数量和把单据改成完成如果分成两次提交，中间一断，数量已经加上，单据仍是草稿。再点一次完成，会再加一次。

这一支：`POST /inbound-orders/{id}/complete` 先把数量加进 `sku.on_hand` 并单独提交，再改状态之前中断。

表：

- `inbound_order`：`id`、`order_no`、`status`、`created_at`
- `inbound_order_line`：`order_id`、`sku_id`、`location_id`、`quantity`

接口：

- `POST /inbound-orders` 建草稿
- `POST /inbound-orders/{id}/lines` 加行
- `POST /inbound-orders/{id}/complete` 完成

正确写法在「第三部分改良版」：表 `inventory` 按货品 + 库位各一行，列有 `quantity` 和 `version`。`version` 本块只写入，乐观锁以后再用。不允许为负放到第四部分。唯一键 `(sku_id, location_id)`。两个库位是两行，10 和 8。完成时加数量和改状态在同一个事务里。

课堂上打开 [第三部分-讲义.html](./第三部分-讲义.html)。时间见 [第三部分-上课教案.md](./第三部分-上课教案.md)。

## 第四部分 先讲 TraceId，再做出库与超卖（第 12 周）

6 课时。周一 1–2 节做数量校验的漏洞。周三先把 TraceId 讲完，再用它看并发超卖。本周不修并发。

### TraceId（周三前大约 50 分钟）

第 10 周不讲。那时还没有两张单同时改同一行库存，拿登录日志演示对不上号，和当天的 Docker 没关系。等到这一周，两路出库同时完成，日志才真的拆不开。

**是什么。** TraceId 是这一次 HTTP 请求的编号。同一次「完成出库」打出的「读到数量 1」和「把数量改成 0」带着同一个号。另一次完成是另一个号。

**解决什么。** 库存只剩 1，两张出库单各出 1，几乎同时点完成。每次完成至少两行日志：读库存一行，更新一行。四行穿在 `docker logs` 里。没有这个号，圈不出哪一次读到了 1、哪一次把数量写成了 -1。第 15 周周二还要用同一个号把一次请求的日志、库和 Redis 串起来，所以这周先讲明白，那天不再从头讲。

**怎么实现。** 不在 Controller 里。三处：

1. `src/main/java/com/eurasia/pro_skill/observability/TraceIdFilter.java`。它在所有接口之前执行。开关打开时，读请求头 `X-Trace-Id`，没有就生成 UUID，放进 MDC 的键 `traceId`，并写回响应头。请求结束把这个键清掉，避免串到下一个请求。
2. `src/main/resources/application.yaml` 的日志格式 `[%X{traceId}]`。`%X{traceId}` 就是从 MDC 取这个键，显示成中括号里的字。下面 `app.lesson.trace-id` 默认 `off`。关掉时过滤器直接放行，不写 MDC，括号是空的。
3. `docker-compose.dev.yml` 的环境变量 `APP_LESSON_TRACE_ID`。容器里用它盖过 yaml。改开关只重建应用容器，不用 `--build`。

课堂上先保持 `off`，做下面的两路同时完成，让学生圈两次请求，圈不开。再 `APP_LESSON_TRACE_ID=on` 重建容器，重做同一次操作。两次完成各有一个号，各自的读取和更新在同一个中括号里。本周看到这个就停，不加锁。

### 内容

出库完成时减少库存。本周留下两个错：不看剩余数量；并发时各自读到还有库存。第二个错只确认原因，乐观锁留到第六部分。

### 具体设计

出库表和入库对称：`outbound_order`、`outbound_order_line`，状态同样先只有 `DRAFT` 和 `COMPLETED`。完成接口 `POST /outbound-orders/{id}/complete`。

先用第三部分把 `A-01-01` 的 `SKU-001` 做成 10。

**不校验剩余。** `app.lesson.outbound-check=off`。完成时直接 `quantity = quantity - n`。再建一张出库 15 的单并完成。该行变成 -5。

学生查：`inventory` 里的负数行。

学生改：`app.lesson.outbound-check=on`。剩余不足时拒绝，错误码 `INSUFFICIENT_STOCK`，数量保持 10。这个修复只挡住「单次就扣穿」，挡不住并发。

**并发超卖。** 把数量重新设成 1。开两个请求，各出库 1，几乎同时完成。两边都读到 1，都认为够，结果变成 -1 或 0 但两张单都完成。`app.lesson.optimistic-lock` 这一周保持 `off`，更新语句是 `where id = ?`，不带 version。

学生查：先在开关关闭时看日志，两次完成圈不开。打开 TraceId 之后，两个号各自的读取都是旧数量 1。本周的任务是确认两次都读到了旧数量，不是去加锁。

课堂明确说：本周不改。周三结束时仓库里留着这次超卖的日志和那一行负数，第十三周用同一操作对照。

## 第五部分 单据状态机（第 13 周周一 1–2 节）

2 课时。依赖第四、第四部分的入库单和出库单。

### 内容

已完成的单据不能再改数量。入库单、出库单用同一套规则。

### 具体设计

漏洞：`COMPLETED` 之后仍允许改行数量。账面已经按原数量加减，单据却变成另一个数，对不上。

先留的错：`app.lesson.order-state=open`。`PATCH /outbound-orders/{id}/lines/{lineId}` 不看状态。把一张已完成、数量 1 的出库单改成 5。库存仍按 1 扣过，单据上写成 5。

学生查：单据行数量和 `inventory.quantity` 的差。

学生改：`app.lesson.order-state=enforced`。状态不是 `DRAFT` 就拒绝，错误码 `ORDER_NOT_EDITABLE`。同一张单再改，返回这个错误，库存和单据保持一致。

本块不增加审批、取消、作废等更多状态。

## 第六部分 乐观锁和事务边界（第 13 周周三 1–4 节）

2 课时。依赖第四部分的并发出库。第三部分的 `version` 列已经在。

### 内容

`@Transactional` 只保证一个事务里的语句一起提交，不保证两个事务读到的数量还有效。

### 具体设计

漏洞：两个事务都在自己的事务里读到剩余 1，都提交 `quantity = 0`。两个事务都成功，库存被扣穿。学生会以为加上 `@Transactional` 就修好了。

先留的错：`app.lesson.optimistic-lock=off`。完成出库的方法已经有 `@Transactional`，更新仍是 `update inventory set quantity = ? where id = ?`。

复现：重复第四部分的两路同时出 1。两个事务都提交，库存变负或两张单都完成。日志里能看到两个 TraceId 都走到了 update。

学生查：两次更新的影响行数都是 1，没有一方失败。

学生改：`app.lesson.optimistic-lock=on`。更新改成 `set quantity = ?, version = version + 1 where id = ? and version = ?`。影响行数为 0 的那一次拒绝，错误码 `STOCK_CONFLICT`，不把数量写成负数。学生再打同一对并发请求，只有一路成功。

失败的一路本块直接拒绝，不在课堂里做自动重试循环。

### 事务边界（同一上午的后两节）

2 课时。依赖第三部分的入库完成。Redis 消息要到第九部分才有，本块用库存流水把同一个漏洞做出来。第九部分再把流水换成消息，漏洞会再出现一次。

### 内容

和入库无关的副作用，不能在主事务提交之前就落到外面。

### 具体设计

漏洞：主事务还可能回滚时，流水已经用另一个事务提交。入库单没了，流水还在。

表 `stock_flow`：`id`、`biz_no`（入库单号）、`sku_id`、`location_id`、`quantity`、`created_at`。

先留的错：`app.lesson.flow-after-commit=off`。`complete` 里调用流水写入，流水服务是 `REQUIRES_NEW`，写完就提交。然后 `app.lesson.inbound-fail-before-status=true` 让主事务抛错回滚。

复现：完成一张入库单。`inbound_order` 没有这张完成单（或状态仍是草稿且数量没加上），`stock_flow` 里已经有这条单号。

学生查：没有对应的完成入库单，却有流水。

学生改：`app.lesson.flow-after-commit=on`。流水和加库存、改状态放在同一个事务里；若要坚持「提交成功后再记」，就注册 `afterCommit` 再写。打开失败开关时，单和流水都不留。关掉失败开关时，单是 `COMPLETED`，流水有且只有一条。

## 第七部分 Redis 缓存（第 14 周周一 1–2 节）

2 课时。依赖第三部分的按库位库存。Compose 在第一部分已经有 MySQL、Adminer 和应用。这一块往同一份文件里加 Redis，主机名用服务名，不用 localhost。

### 内容

库存查询先读缓存。缓存不是库存的来源，库才是。

### 具体设计

漏洞：出库已经把库里的数量改了，缓存还留着旧值。页面和库不一致。

键：`inv:{skuId}:{locationId}`。`GET /inventories?skuId=&locationId=` 未命中时查库并写入，命中时直接返回。

先留的错：`app.lesson.cache-evict=off`。出库完成只更新 `inventory`，不删除这个键。

复现：先查询一次，让缓存写入 10。再完成出库 3。接口再查询仍返回 10，Adminer 里已是 7。

学生查：Redis 里的值和 `inventory.quantity`。

学生改：`app.lesson.cache-evict=on`。库存更新成功后删除对应键。同一查询再打，返回 7。

本块不设置很长的讲解来比较各种过期时间。可以给键一个较短 TTL，作为删键失败时的兜底，但不能靠 TTL 代替删除。

## 第八部分 Redis 锁和防重复提交（第 14 周周三 1–4 节）

2 课时。依赖第六部分。乐观锁已经能挡住第四部分那种「同时更新同一行」。这一块演示另一种漏法：两张单都通过了「还有库存」的检查。

### 内容

检查剩余和扣减必须落在同一把锁里。锁按货品 + 库位，不按整张出库单，也不用一把全局锁。

### 具体设计

漏洞：先读数量判断够不够，判断完才去抢锁或直接扣减。两个请求都在加锁前读到够，于是都进入后面的步骤。

先留的错：`app.lesson.stock-lock=after-check`。完成出库时先 `select quantity`，够了才 `SET lock:inv NX`。两张单各出库 1，库存只有 1。两边都读到 1，都认为通过了检查。

学生查：两张出库单的状态和日志。两条 TraceId 都打印了「检查通过」。

学生改：`app.lesson.stock-lock=sku-location`。进入检查之前就按 `lock:inv:{skuId}:{locationId}` 加锁，检查、扣减、释放都在锁内。过期时间要盖住这次完成，释放时核对持有者，避免删掉别人的锁。同一对请求再打，只有一张单完成，另一张在检查时就被拒绝。

第六部分的 version 条件保留。锁减少冲突，乐观锁仍是最后一道。

### 防重复提交（同一上午的后两节）

2 课时。依赖第四部分的出库完成。

### 内容

同一张出库单，完成按钮点两次，只能扣一次。

### 具体设计

漏洞：完成接口没有按单号记住「已经扣过」。两次请求各自进入扣减，库存扣两次。这和第八部分的并发锁不是同一个问题：第二次是用户重复提交同一单号，不是两张不同的单。

先留的错：`app.lesson.submit-once=off`。`POST /outbound-orders/{id}/complete` 不看这张单是否已经完成，也不写 Redis。对同一单号连调两次。库存少了两倍数量，或 `stock_flow` 出现同一 `biz_no` 的两条扣减。

学生查：同一单号的两条扣减。出库单如果第一次已是 `COMPLETED`，第二次仍又减了库存。

学生改：`app.lesson.submit-once=on`。完成前 `SET outbound:done:{orderNo} NX`。第二次拿不到键，直接返回已完成，不再扣减。数据库侧同时拒绝非 `DRAFT` 的完成，和第五部分的状态机接上。Redis 挡住短时间连点，状态机挡住键过期之后的再提交。

## 第九部分 Redis 异步（第 15 周周一 1–4 节）

4 课时。依赖第三部分的入库完成，以及第六部分的事务边界。

### 内容

入库完成后发一条消息，消费者写库存流水。用 Redis Stream，不用 Pub/Sub，不用 RabbitMQ。

### 具体设计

Stream 名 `wms:inbound:completed`。消息体至少有 `orderNo`、`skuId`、`locationId`、`quantity`。消费者组处理这条消息，写入 `stock_flow`。

两个漏洞分两步演示。

**发在事务里。** `app.lesson.publish-after-commit=off`。`complete` 还在事务中就 `XADD`，随后主事务按第六部分的失败开关回滚。消费者已经把流水写出去了。现象和第六部分一样：没有完成的入库单，却有流水。学生改成事务 `afterCommit` 再 `XADD`。回滚时 Stream 里没有这条消息。

**消费者不认单号。** `app.lesson.consume-once=off`。同一条消息投递两次（或消费者处理成功但没 ACK，再读到一次），`stock_flow` 出现两笔相同 `biz_no`。

学生查：重复流水的单号。

学生改：`app.lesson.consume-once=on`。处理前用入库单号做幂等，`SET inbound:consumed:{orderNo} NX`，或给 `stock_flow.biz_no` 加唯一约束。第二次处理直接跳过。同一条消息再投递，流水仍是一笔。

第六部分的数据库流水可以留着对照。从这一块起，完成入库后的流水以消息这条路径为准。

## 第十部分 MinIO（第 15 周周一 7–10 节）

4 课时。依赖第三部分的入库单。

### 内容

入库单附件。库里只存对象的 key，不存某台机器上的绝对路径。

### 具体设计

漏洞：文件写在应用本机磁盘，库里记 `/tmp/wms/...` 或项目目录下的路径。换一台机器，或应用跑进容器，这个路径不存在，下载 404。

先留的错：`app.lesson.file-store=local`。`POST /inbound-orders/{id}/attachments` 把文件写到本地目录，`inbound_attachment.file_path` 存绝对路径。`GET` 按这个路径读文件。

复现：上传一份附件，在 Adminer 看到本地路径，接口能下载。然后停掉本机进程，改用容器里的应用再下载，或删掉本机那个目录后再下载，返回 404。库里的路径还在。

学生查：`file_path` 是本机路径，容器或另一台机器上没有这个文件。

学生改：`app.lesson.file-store=minio`。Compose 增加 MinIO。上传写入 bucket `wms`，对象 key 为 `inbound/{orderNo}/{filename}`。表里改存 `object_key`，不再存绝对路径。在容器里用同一 key 仍能下载。

本块只做这一类附件。不做成通用网盘。

## 第十一部分 用 TraceId 排错（第 15 周周二）

6 课时。不讲新组件，也不再讲 TraceId 是什么。第 12 周周三已经讲过它解决什么、代码在哪。这天把前面三处开关拨回缺陷路径，学生只靠已经会用的 TraceId 把一次请求串起来，再改回去。

作业二的缺陷记录在这天写完再交。

### 内容

三个已经讲过的事故。每个事故学生要回答：是哪一次请求造成的，库和缓存（或流水）现在是什么。

### 具体设计

| 拨回的开关 | 现场 | 学生要串起来的东西 |
|------------|------|--------------------|
| `app.lesson.optimistic-lock=off` | 两路出库把数量打负 | 两个 TraceId 的读取和更新，以及 `inventory` 那一行 |
| `app.lesson.cache-evict=off` | 页面仍是旧库存 | 同一次出库的 TraceId、MySQL 的新数量、Redis 里的旧值 |
| `app.lesson.consume-once=off` | 同一入库单两笔流水 | 这一条消息对应的 TraceId，和 `stock_flow` 里重复的 `biz_no` |

操作和第五、九、十二部分相同。差别是这一次不先告诉学生开关名，让他们从日志里的 TraceId 追到库和 Redis。

查清后把开关拨回修复路径，再做同一操作：并发只有一路成功，查询到的是新库存，流水只有一笔。

## 第十二部分 慢查询（第 15 周周三）

4 课时。依赖第三部分的 `inventory`。作业三在这天布置。

### 内容

库存列表为什么超过 3 秒。先让它慢，再加索引和分页。

### 具体设计

漏洞：`GET /inventories` 一次 `select` 全表，过滤条件没有索引。数据一多，查询超过 3 秒。

先留的错：`app.lesson.inventory-query=full`。列表不接 `page`、`size`，SQL 不带 `limit`。准备一份只在这堂课导入的库存数据，行数要能让这次查询稳定超过 3 秒。不要把这批数据写进日常启动迁移，避免前面各块的课堂被拖慢。

复现：调用列表接口，记录耗时。让学生在 MySQL 里看这次语句是全表扫描。

学生查：慢查询日志或 `EXPLAIN`。

学生改：`app.lesson.inventory-query=page`。列表必须带分页。按实际过滤字段加索引，已有的 `(sku_id, location_id)` 唯一键继续留着。同一请求耗时降下来，响应里是一页而不是全表。

## 第十三部分 Prometheus 与 Grafana（第 15 周周四 1–4 节）

4 课时。依赖第四部分的出库完成，以及第十二部分的压测方式。压测用 JMeter 或 k6，二选一在课堂上定下来，全组用同一种。

### 内容

只知道接口变慢时，看不出慢在出库，也看不出有多少次因为库存不足被拒绝。

### 具体设计

漏洞：Actuator 现在只暴露 `health` 和 `info`。压测之后没有出库耗时，也没有拒绝次数。

先留的错：`app.lesson.metrics=off`。不注册业务指标。对出库完成压一轮，Grafana 或指标端点上看不到这条接口。

学生查：压测结果只有总耗时，对不上是完成出库慢，还是拒绝变多。

学生改：`app.lesson.metrics=on`。

- 计时：出库完成的耗时
- 计数：出库因 `INSUFFICIENT_STOCK` 或 `STOCK_CONFLICT` 被拒绝的次数
- 暴露 Prometheus 端点

Grafana 使用一份已经配好的面板，学生要能指出出库耗时和拒绝次数。不要求学生从空白面板开始画，也不做告警规则。

Zipkin 用一次现成示例看一条 TraceId 跨了哪些 span，不作为作业交付。

## 第十四部分 把后加的服务收进同一份 Compose（第 15 周周四 7–10 节）

4 课时。依赖第一部分的应用基座，以及第七部分的 Redis、第十部分的 MinIO。镜像和「localhost 连不上 MySQL」已经在第一部分做过，这里不再新讲 Dockerfile。

### 内容

后面各块往 Compose 里加服务时，容易又写成 `localhost`。这一块把应用、MySQL、Redis、MinIO 收成第一部分那一份 Compose，逐个核对主机名。

### 具体设计

漏洞：Redis 或 MinIO 的地址在容器里写成 `localhost`。应用容器去连自己，Redis 容器其实是健康的。

先留的错：把 `app.lesson` 里对应主机临时改回 `localhost`，只改新加的那个服务，MySQL 仍用 `mysql`。

复现：应用能连上数据库，但缓存或附件报连接失败。

学生查：`docker ps` 里 Redis、MinIO 是 Up，应用日志里的主机名是 `localhost`。

学生改：改回服务名，仍用第一部分的 `docker-compose.dev.yml` 启动。不另写第二套 Compose。Nginx 在下一块加进同一份文件。

## 第十五部分 Nginx（第 15 周周五）

4 课时。依赖第一部分的应用容器。Nginx 加进同一份 Compose。

### 内容

浏览器只访问 Nginx。页面走 `/`，接口走 `/api`。Nginx 不做登录、不做库存计算。

### 具体设计

本仓库原来没有前端。这一块只加一个静态页：登录、按货品和库位查库存。业务仍在后端。

漏洞：页面里的接口写成 `http://localhost:8080`。在本机打开碰巧能用。改用服务器地址打开页面时，浏览器仍去访问打开页面的那台电脑自己的 8080，接口失败。

先留的错：`app.lesson.api-base=absolute`。静态页请求 `http://localhost:8080/auth/login` 和库存接口。Nginx 只托管页面，没有把 `/api` 转到应用。

复现：用机器的局域网地址或服务器地址打开页面，登录失败。浏览器网络面板里，请求目标是 `localhost:8080`。

学生查：浏览器里的请求 URL。

学生改：`app.lesson.api-base=/api`。页面改为请求 `/api/...`。Nginx：

- `/` 指向静态页
- `/api/` 反代到 `app:8080`，并去掉前缀 `/api`

再用服务器地址打开，登录和查询都成功。后端不需要知道自己前面有 Nginx，安全配置里已有的登录和 Swagger 放行保持不变。

## 第十六部分 Linux（第 16 周周一至周二）

14 课时。周一全天 8 课时，周二 6 课时。依赖第一部分的 Compose 基座，第十四部分收进来的 Redis 和 MinIO，以及第十五部分的 Nginx。

### 内容

服务器上用同一份 Compose 和同一份 `.env`，不另写一套配置。

### 具体设计

漏洞：本机能开，是因为开发机有 `application-local.properties`、本机端口和本机 Docker。把仓库拷到 Linux 后，这些前提没有了，容器起不来，或端口和环境变量和本机不一致。

先留的错：部署说明仍写着在服务器上创建 `application-local.properties`，JDBC 仍有人改回 `localhost`。用这份错误说明在 Linux 上启动。

复现：服务器上 `docker ps` 里应用容器反复重启，或 Nginx 开了页但 `/api` 失败。日志里的主机名、端口和 `.env` 对不上。

学生查：`docker ps`、应用容器日志、服务器上的 `.env`。

学生改：只保留一份 Compose。数据库、Redis、MinIO、应用端口、密码都从 `.env` 读取。JDBC 主机保持服务名 `mysql`。开发机和 Linux 用同一份文件，只允许 `.env` 里的端口和密码不同。服务器上同一套命令启动后，页面、登录、入库完成、出库完成、附件下载都可用。

周二下课前冻结功能。之后只修部署和缺陷，不加新接口。
