# 综合能力实训 · 备课教案

课堂案例是这个 WMS。学生自己的大作业是另外 15 个选题，验收标准和这里对齐，不要在本仓库里做那 15 个题。

这份教案按新内容分块。周次只标在每一块标题上，用来对课表，不是目录本身。后一块只用前一块已经跑通的结果。

## 教法

每一块都按这四步，不要先把正确实现交给学生：

1. 讲清不这么设计的漏洞。
2. 项目里先留着这个错，按下面的操作就能复现。
3. 学生自己查：日志、库、页面、TraceId。
4. 学生自己改。同一操作不再出错。

代码里同时留缺陷路径和修复路径，用配置开关切换，默认在讲这一块时走缺陷路径。学生改完后，后面的课默认走修复路径，开关仍能拨回去。第 15 周周二排错时，就把对应开关拨回缺陷路径。

开关都写在 `application.yaml` 的 `app.lesson` 下。库上的约束（唯一索引、乐观锁条件）用前后两次迁移或两次提交演示，不靠开关把已经加上的唯一索引再关掉。

## 本分支留下什么

留下能跑的基础，第 10 周用来接新内容：

- 注册登录、JWT、用户 CRUD
- 仓库–库区–库位，Flyway V1–V6
- 演示账号 `admin` / `Admin@123`，仓库 `WH-001`（华东原料仓），库位 `A-01-01`、`A-01-02`、`B-01-01`
- 单测、`api-contract/http`、Compose 里的 MySQL 和 Adminer
- 分层约定：`layered-architecture.md`

上学期的用户 CRUD 讲义、FR-01 作业教案、Postman 性能集合、个人介绍材料，已从本分支删除。那些内容不再当新课讲。

## 不做

盘点、FIFO、移库、复杂报表。异步不用 RabbitMQ，也不用 Redis Pub/Sub，用 Stream。Zipkin 只演示。学生不自建告警，不手画全套 Grafana 仪表盘。Nginx 只做反代，不算业务。

## 第一部分 接入现有系统，埋 TraceId（第 10 周）

6 课时。周一 1–2 节分组并跑通，周三 1–4 节让日志能对上一次请求。

### 内容

学生把 main 在自己机器上跑起来，分成小组，并给每次请求一个 TraceId。本周还没有出库，不演示库存被打负。库存那场留到第五部分制造、第十四部分再查。

### 具体设计

现有日志只有类名和 SQL，没有请求号。两个请求同时打进来，日志按时间穿插，看不出哪一行属于哪一次。

先留的错：不加 Filter，日志 pattern 里也没有 traceId。`app.lesson.trace-id=off`。

复现：两个终端同时调已有接口，例如 `GET /warehouses`（先 `POST /auth/login`，账号 `admin`，密码 `Admin@123`）。把两份日志放在一起，SQL 对不上是哪一次登录发出的。

学生查：应用日志。本周还没有库存行可对。

学生改：

- `OncePerRequestFilter` 读请求头 `X-Trace-Id`，没有就生成 UUID，放入 MDC，写回响应头。
- 日志 pattern 加上 `%X{traceId}`。
- `app.lesson.trace-id=on` 后，再并发打同一接口，同一请求的登录、鉴权、SQL 带同一个号。

分组在周一完成。每组确定自己大作业的选题，并指定谁负责后面作业二的哪一个模块。课堂案例仍全组一起跟着做。

作业一在这周布置。

## 第二部分 货品 SKU（第 11 周周一 1–2 节）

2 课时。依赖第一部分已经能登录、能开库。

### 内容

货品主数据。只做编码、名称、单位。不做多规格、不做批次。

### 具体设计

漏洞：编码没有唯一约束时，两条货品可以都叫 `SKU-001`。入库、出库无法知道扣的是哪一条。

先留的错：Flyway 新建 `sku`，字段 `id`、`code`、`name`、`unit`、`created_at`。`code` 只有普通索引，没有唯一索引。`POST /skus` 应用层也不查重。

复现：Swagger 连建两次 `{ "code": "SKU-001", "name": "轴承", "unit": "个" }`。Adminer 里 `sku` 出现两行相同编码。

学生查：`sku` 表。

学生改：新迁移给 `code` 加唯一索引。第二次创建返回业务错误，例如 `SKU_CODE_DUPLICATED`。库里已有的重复数据要先删掉，迁移才能通过。这一步用提交前后对比，不用开关把唯一索引再关掉。

接口：

- `POST /skus`
- `GET /skus`

作业二在这周布置。作业一在周三截止，核心表初稿至少要有货品，库存和入库表在当天后两节补上。

## 第三部分 库存账（第 11 周周三 1–2 节）

2 课时。依赖第二部分已经有货品，以及现成库位 `A-01-01`、`A-01-02`。

### 内容

库存记在哪。正确模型是货品 + 库位 + 数量 + version。version 这一列先建上，第十三周的乐观锁才用它。本块不讲锁。

### 具体设计

漏洞：数量若写成 `sku.on_hand` 一个总数，同一货品放到两个库位时，账面要么被后一次覆盖，要么只有一个合计数，对不上每个库位。

先留的错：`app.lesson.stock-model=on-sku`。给 `sku` 加 `on_hand`。入库动作先做成「把数量加到货品上」，不写库位。

复现：

1. `SKU-001` 放到 `A-01-01`，数量 10。`on_hand` 变成 10。
2. 同一货品再放到 `A-01-02`，数量 8。`on_hand` 变成 18，或者被写成 8。
3. 问学生：`A-01-01` 现在应有多少。表上答不出来。

学生查：`sku.on_hand` 和两个库位。页面或 Swagger 返回的总数对不上分库位。

学生改：`app.lesson.stock-model=by-location`。新表 `inventory`：

| 列 | 说明 |
|----|------|
| id | 主键 |
| sku_id | 货品 |
| location_id | 库位，指向已有 `warehouse_location` |
| quantity | 该库位数量，不允许为负的约束放到第五部分 |
| version | 从 0 开始，本块只写入，不参与更新条件 |

唯一键 `(sku_id, location_id)`。查询按货品加库位返回一行。两个库位是两行，10 和 8，不再互相覆盖。

## 第四部分 入库（第 11 周周三 3–4 节）

2 课时。依赖第三部分的库存行。

### 内容

入库单完成时增加对应库位的库存。状态只做 `DRAFT` 和 `COMPLETED`。附件留到第十三部分。

### 具体设计

漏洞：加库存和把单据改成完成，如果是两次提交，中间失败就会库存已经加上、单据仍未完成。下次有人再点完成，会再加一次。

先留的错：`app.lesson.inbound-tx=split`。`POST /inbound-orders/{id}/complete` 里先更新 `inventory.quantity` 并提交，再把 `inbound_order.status` 改成 `COMPLETED`。开关 `app.lesson.inbound-fail-before-status=true` 时，两次提交之间抛异常。

表：

- `inbound_order`：`id`、`order_no`、`status`、`created_at`
- `inbound_order_line`：`order_id`、`sku_id`、`location_id`、`quantity`

接口：

- `POST /inbound-orders` 建草稿，生成单号
- `POST /inbound-orders/{id}/lines` 加行
- `POST /inbound-orders/{id}/complete` 完成

复现：建一张草稿，一行 `SKU-001`、`A-01-01`、数量 10，打开失败开关后点完成。Adminer 里该库位数量已是 10，单据状态仍是 `DRAFT`。

学生查：半成功的单。对 `inventory.quantity` 和 `inbound_order.status`。

学生改：`app.lesson.inbound-tx=atomic`。加库存和改状态放进同一个 `@Transactional`。失败开关仍打开时，数量回到完成前，单据仍是草稿。关掉失败开关后，数量加上，单据变成 `COMPLETED`。

## 第五部分 出库与超卖（第 12 周）

6 课时。周一 1–2 节做数量校验的漏洞，周三 1–4 节做并发超卖。本周不修并发。

### 内容

出库完成时减少库存。本周留下两个错：不看剩余数量；并发时各自读到还有库存。第二个错只确认原因，乐观锁留到第七部分。

### 具体设计

出库表和入库对称：`outbound_order`、`outbound_order_line`，状态同样先只有 `DRAFT` 和 `COMPLETED`。完成接口 `POST /outbound-orders/{id}/complete`。

先用第四部分把 `A-01-01` 的 `SKU-001` 做成 10。

**不校验剩余。** `app.lesson.outbound-check=off`。完成时直接 `quantity = quantity - n`。再建一张出库 15 的单并完成。该行变成 -5。

学生查：`inventory` 里的负数行。

学生改：`app.lesson.outbound-check=on`。剩余不足时拒绝，错误码 `INSUFFICIENT_STOCK`，数量保持 10。这个修复只挡住「单次就扣穿」，挡不住并发。

**并发超卖。** 把数量重新设成 1。开两个请求，各出库 1，几乎同时完成。两边都读到 1，都认为够，结果变成 -1 或 0 但两张单都完成。`app.lesson.optimistic-lock` 这一周保持 `off`，更新语句是 `where id = ?`，不带 version。

学生查：日志里的两次请求。第一部分若已打开 TraceId，两次完成各有一个号。本周的任务是确认两次都读到了旧数量，不是去加锁。

课堂明确说：本周不改。周三结束时仓库里留着这次超卖的日志和那一行负数，第十三周用同一操作对照。

## 第六部分 单据状态机（第 13 周周一 1–2 节）

2 课时。依赖第四、第五部分的入库单和出库单。

### 内容

已完成的单据不能再改数量。入库单、出库单用同一套规则。

### 具体设计

漏洞：`COMPLETED` 之后仍允许改行数量。账面已经按原数量加减，单据却变成另一个数，对不上。

先留的错：`app.lesson.order-state=open`。`PATCH /outbound-orders/{id}/lines/{lineId}` 不看状态。把一张已完成、数量 1 的出库单改成 5。库存仍按 1 扣过，单据上写成 5。

学生查：单据行数量和 `inventory.quantity` 的差。

学生改：`app.lesson.order-state=enforced`。状态不是 `DRAFT` 就拒绝，错误码 `ORDER_NOT_EDITABLE`。同一张单再改，返回这个错误，库存和单据保持一致。

本块不增加审批、取消、作废等更多状态。

## 第七部分 乐观锁（第 13 周周三 1–2 节）

2 课时。依赖第五部分的并发出库。第三部分的 `version` 列已经在。

### 内容

`@Transactional` 只保证一个事务里的语句一起提交，不保证两个事务读到的数量还有效。

### 具体设计

漏洞：两个事务都在自己的事务里读到剩余 1，都提交 `quantity = 0`。两个事务都成功，库存被扣穿。学生会以为加上 `@Transactional` 就修好了。

先留的错：`app.lesson.optimistic-lock=off`。完成出库的方法已经有 `@Transactional`，更新仍是 `update inventory set quantity = ? where id = ?`。

复现：重复第五部分的两路同时出 1。两个事务都提交，库存变负或两张单都完成。日志里能看到两个 TraceId 都走到了 update。

学生查：两次更新的影响行数都是 1，没有一方失败。

学生改：`app.lesson.optimistic-lock=on`。更新改成 `set quantity = ?, version = version + 1 where id = ? and version = ?`。影响行数为 0 的那一次拒绝，错误码 `STOCK_CONFLICT`，不把数量写成负数。学生再打同一对并发请求，只有一路成功。

失败的一路本块直接拒绝，不在课堂里做自动重试循环。

## 第八部分 事务边界（第 13 周周三 3–4 节）

2 课时。依赖第四部分的入库完成。Redis 消息要到第十二部分才有，本块用库存流水把同一个漏洞做出来。第十二部分再把流水换成消息，漏洞会再出现一次。

### 内容

和入库无关的副作用，不能在主事务提交之前就落到外面。

### 具体设计

漏洞：主事务还可能回滚时，流水已经用另一个事务提交。入库单没了，流水还在。

表 `stock_flow`：`id`、`biz_no`（入库单号）、`sku_id`、`location_id`、`quantity`、`created_at`。

先留的错：`app.lesson.flow-after-commit=off`。`complete` 里调用流水写入，流水服务是 `REQUIRES_NEW`，写完就提交。然后 `app.lesson.inbound-fail-before-status=true` 让主事务抛错回滚。

复现：完成一张入库单。`inbound_order` 没有这张完成单（或状态仍是草稿且数量没加上），`stock_flow` 里已经有这条单号。

学生查：没有对应的完成入库单，却有流水。

学生改：`app.lesson.flow-after-commit=on`。流水和加库存、改状态放在同一个事务里；若要坚持「提交成功后再记」，就注册 `afterCommit` 再写。打开失败开关时，单和流水都不留。关掉失败开关时，单是 `COMPLETED`，流水有且只有一条。

## 第九部分 Redis 缓存（第 14 周周一 1–2 节）

2 课时。依赖第三部分的按库位库存。Compose 从这一块开始加上 Redis。之前的 Compose 仍只有 MySQL 和 Adminer。

### 内容

库存查询先读缓存。缓存不是库存的来源，库才是。

### 具体设计

漏洞：出库已经把库里的数量改了，缓存还留着旧值。页面和库不一致。

键：`inv:{skuId}:{locationId}`。`GET /inventories?skuId=&locationId=` 未命中时查库并写入，命中时直接返回。

先留的错：`app.lesson.cache-evict=off`。出库完成只更新 `inventory`，不删除这个键。

复现：先查询一次，让缓存写入 10。再完成出库 3。接口再查询仍返回 10，Adminer 里已是 7。

学生查：Redis 里的值和 `inventory.quantity`。

学生改：`app.lesson.cache-evict=on`。库存更新成功后删除对应键。同一查询再打，返回 7。

本块不设置很长的讲解来比较各种过期时间。可以给键一个较短 TTL，作为删键失败时的兜底，但不能靠 TTL 代替删除。

## 第十部分 Redis 锁（第 14 周周三 1–2 节）

2 课时。依赖第七部分。乐观锁已经能挡住第五部分那种「同时更新同一行」。这一块演示另一种漏法：两张单都通过了「还有库存」的检查。

### 内容

检查剩余和扣减必须落在同一把锁里。锁按货品 + 库位，不按整张出库单，也不用一把全局锁。

### 具体设计

漏洞：先读数量判断够不够，判断完才去抢锁或直接扣减。两个请求都在加锁前读到够，于是都进入后面的步骤。

先留的错：`app.lesson.stock-lock=after-check`。完成出库时先 `select quantity`，够了才 `SET lock:inv NX`。两张单各出库 1，库存只有 1。两边都读到 1，都认为通过了检查。

学生查：两张出库单的状态和日志。两条 TraceId 都打印了「检查通过」。

学生改：`app.lesson.stock-lock=sku-location`。进入检查之前就按 `lock:inv:{skuId}:{locationId}` 加锁，检查、扣减、释放都在锁内。过期时间要盖住这次完成，释放时核对持有者，避免删掉别人的锁。同一对请求再打，只有一张单完成，另一张在检查时就被拒绝。

第七部分的 version 条件保留。锁减少冲突，乐观锁仍是最后一道。

## 第十一部分 防重复提交（第 14 周周三 3–4 节）

2 课时。依赖第五部分的出库完成。

### 内容

同一张出库单，完成按钮点两次，只能扣一次。

### 具体设计

漏洞：完成接口没有按单号记住「已经扣过」。两次请求各自进入扣减，库存扣两次。这和第十部分的并发锁不是同一个问题：第二次是用户重复提交同一单号，不是两张不同的单。

先留的错：`app.lesson.submit-once=off`。`POST /outbound-orders/{id}/complete` 不看这张单是否已经完成，也不写 Redis。对同一单号连调两次。库存少了两倍数量，或 `stock_flow` 出现同一 `biz_no` 的两条扣减。

学生查：同一单号的两条扣减。出库单如果第一次已是 `COMPLETED`，第二次仍又减了库存。

学生改：`app.lesson.submit-once=on`。完成前 `SET outbound:done:{orderNo} NX`。第二次拿不到键，直接返回已完成，不再扣减。数据库侧同时拒绝非 `DRAFT` 的完成，和第六部分的状态机接上。Redis 挡住短时间连点，状态机挡住键过期之后的再提交。

## 第十二部分 Redis 异步（第 15 周周一 1–4 节）

4 课时。依赖第四部分的入库完成，以及第八部分的事务边界。

### 内容

入库完成后发一条消息，消费者写库存流水。用 Redis Stream，不用 Pub/Sub，不用 RabbitMQ。

### 具体设计

Stream 名 `wms:inbound:completed`。消息体至少有 `orderNo`、`skuId`、`locationId`、`quantity`。消费者组处理这条消息，写入 `stock_flow`。

两个漏洞分两步演示。

**发在事务里。** `app.lesson.publish-after-commit=off`。`complete` 还在事务中就 `XADD`，随后主事务按第八部分的失败开关回滚。消费者已经把流水写出去了。现象和第八部分一样：没有完成的入库单，却有流水。学生改成事务 `afterCommit` 再 `XADD`。回滚时 Stream 里没有这条消息。

**消费者不认单号。** `app.lesson.consume-once=off`。同一条消息投递两次（或消费者处理成功但没 ACK，再读到一次），`stock_flow` 出现两笔相同 `biz_no`。

学生查：重复流水的单号。

学生改：`app.lesson.consume-once=on`。处理前用入库单号做幂等，`SET inbound:consumed:{orderNo} NX`，或给 `stock_flow.biz_no` 加唯一约束。第二次处理直接跳过。同一条消息再投递，流水仍是一笔。

第八部分的数据库流水可以留着对照。从这一块起，完成入库后的流水以消息这条路径为准。

## 第十三部分 MinIO（第 15 周周一 7–10 节）

4 课时。依赖第四部分的入库单。

### 内容

入库单附件。库里只存对象的 key，不存某台机器上的绝对路径。

### 具体设计

漏洞：文件写在应用本机磁盘，库里记 `/tmp/wms/...` 或项目目录下的路径。换一台机器，或应用跑进容器，这个路径不存在，下载 404。

先留的错：`app.lesson.file-store=local`。`POST /inbound-orders/{id}/attachments` 把文件写到本地目录，`inbound_attachment.file_path` 存绝对路径。`GET` 按这个路径读文件。

复现：上传一份附件，在 Adminer 看到本地路径，接口能下载。然后停掉本机进程，改用容器里的应用再下载，或删掉本机那个目录后再下载，返回 404。库里的路径还在。

学生查：`file_path` 是本机路径，容器或另一台机器上没有这个文件。

学生改：`app.lesson.file-store=minio`。Compose 增加 MinIO。上传写入 bucket `wms`，对象 key 为 `inbound/{orderNo}/{filename}`。表里改存 `object_key`，不再存绝对路径。在容器里用同一 key 仍能下载。

本块只做这一类附件。不做成通用网盘。

## 第十四部分 用 TraceId 排错（第 15 周周二）

6 课时。不讲新组件。把前面三处开关拨回缺陷路径，学生只靠 TraceId 把一次请求串起来，再改回去。

作业二的缺陷记录在这天写完再交。

### 内容

三个已经讲过的事故。每个事故学生要回答：是哪一次请求造成的，库和缓存（或流水）现在是什么。

### 具体设计

| 拨回的开关 | 现场 | 学生要串起来的东西 |
|------------|------|--------------------|
| `app.lesson.optimistic-lock=off` | 两路出库把数量打负 | 两个 TraceId 的读取和更新，以及 `inventory` 那一行 |
| `app.lesson.cache-evict=off` | 页面仍是旧库存 | 同一次出库的 TraceId、MySQL 的新数量、Redis 里的旧值 |
| `app.lesson.consume-once=off` | 同一入库单两笔流水 | 这一条消息对应的 TraceId，和 `stock_flow` 里重复的 `biz_no` |

操作和第五、九、十二部分相同。差别是这一次不先告诉学生开关名，让他们从日志里的 TraceId 追到库和 Redis。

查清后把开关拨回修复路径，再做同一操作：并发只有一路成功，查询到的是新库存，流水只有一笔。

## 第十五部分 慢查询（第 15 周周三）

4 课时。依赖第三部分的 `inventory`。作业三在这天布置。

### 内容

库存列表为什么超过 3 秒。先让它慢，再加索引和分页。

### 具体设计

漏洞：`GET /inventories` 一次 `select` 全表，过滤条件没有索引。数据一多，查询超过 3 秒。

先留的错：`app.lesson.inventory-query=full`。列表不接 `page`、`size`，SQL 不带 `limit`。准备一份只在这堂课导入的库存数据，行数要能让这次查询稳定超过 3 秒。不要把这批数据写进日常启动迁移，避免前面各块的课堂被拖慢。

复现：调用列表接口，记录耗时。让学生在 MySQL 里看这次语句是全表扫描。

学生查：慢查询日志或 `EXPLAIN`。

学生改：`app.lesson.inventory-query=page`。列表必须带分页。按实际过滤字段加索引，已有的 `(sku_id, location_id)` 唯一键继续留着。同一请求耗时降下来，响应里是一页而不是全表。

## 第十六部分 Prometheus 与 Grafana（第 15 周周四 1–4 节）

4 课时。依赖第五部分的出库完成，以及第十五部分的压测方式。压测用 JMeter 或 k6，二选一在课堂上定下来，全组用同一种。

### 内容

只知道接口变慢时，看不出慢在出库，也看不出有多少次因为库存不足被拒绝。

### 具体设计

漏洞：Actuator 现在只暴露 `health` 和 `info`。压测之后没有出库耗时，也没有拒绝次数。

先留的错：`app.lesson.metrics=off`。不注册业务指标。对出库完成压一轮，Grafana 或指标端点上看不到这条接口。

学生查：压测结果只有总耗时，对不上是完成出库慢，还是拒绝变多。

学生改：`app.lesson.metrics=on`。

- 计时：出库完成的耗时
- 计数：出库因 `INSUFFICIENT_STOCK` 或 `STOCK_CONFLICT` 被拒绝的次数
- 暴露 Prometheus 端点

Grafana 使用一份已经配好的面板，学生要能指出出库耗时和拒绝次数。不要求学生从空白面板开始画，也不做告警规则。

Zipkin 用一次现成示例看一条 TraceId 跨了哪些 span，不作为作业交付。

## 第十七部分 Docker（第 15 周周四 7–10 节）

4 课时。依赖应用已经能在本机连上 Compose 里的 MySQL。

### 内容

应用自己的镜像。容器里的 `localhost` 不是宿主机，也不是 MySQL 那个容器。

### 具体设计

漏洞：数据源地址写 `localhost:3306`。应用打包进镜像后，它连的是自己容器里的 3306，MySQL 在旁边那个服务上。

先留的错：`app.lesson.datasource-host=localhost`。Dockerfile 用多阶段构建打出镜像，Compose 增加 `app` 服务，环境变量仍把 JDBC 指到 `localhost`。

复现：`docker compose up` 之后看 `app` 的日志，连接被拒绝或未知数据库。MySQL 容器是健康的。

学生查：`app` 容器日志，以及它的环境变量里主机名是 `localhost`。

学生改：`app.lesson.datasource-host=mysql`。JDBC 主机改成 Compose 服务名 `mysql`。同一份 Compose 再启动，应用能完成 Flyway，`/actuator/health` 正常。账号密码从环境变量读，不写进镜像。

## 第十八部分 Nginx（第 15 周周五）

4 课时。依赖第十七部分的应用容器。

### 内容

浏览器只访问 Nginx。页面走 `/`，接口走 `/api`。Nginx 不做登录、不做库存计算。

### 具体设计

本仓库原来没有前端。这一块只加一个静态页：登录、按货品和库位查库存。业务仍在后端。

漏洞：页面里的接口写成 `http://localhost:8080`。在本机打开碰巧能用。改用服务器地址打开页面时，浏览器仍去访问打开页面的那台电脑自己的 8080，接口失败。

先留的错：`app.lesson.api-base=absolute`。静态页请求 `http://localhost:8080/auth/login` 和库存接口。Nginx 只托管页面，没有把 `/api` 转到应用。

复现：用机器的局域网地址或服务器地址打开页面，登录失败。浏览器网络面板里，请求目标是 `localhost:8080`。

学生查：浏览器里的请求 URL。

学生改：`app.lesson.api-base=/api`。页面改为请求 `/api/...`。Nginx：

- `/` 指向静态页
- `/api/` 反代到 `app:8080`，并去掉前缀 `/api`

再用服务器地址打开，登录和查询都成功。后端不需要知道自己前面有 Nginx，安全配置里已有的登录和 Swagger 放行保持不变。

## 第十九部分 Linux（第 16 周周一至周二）

14 课时。周一全天 8 课时，周二 6 课时。依赖第十七、十八部分已经在本机用 Compose 跑通应用、MySQL、Redis、MinIO、Nginx。

### 内容

服务器上用同一份 Compose 和同一份 `.env`，不另写一套配置。

### 具体设计

漏洞：本机能开，是因为开发机有 `application-local.properties`、本机端口和本机 Docker。把仓库拷到 Linux 后，这些前提没有了，容器起不来，或端口和环境变量和本机不一致。

先留的错：部署说明仍写着在服务器上创建 `application-local.properties`，JDBC 仍有人改回 `localhost`。用这份错误说明在 Linux 上启动。

复现：服务器上 `docker ps` 里应用容器反复重启，或 Nginx 开了页但 `/api` 失败。日志里的主机名、端口和 `.env` 对不上。

学生查：`docker ps`、应用容器日志、服务器上的 `.env`。

学生改：只保留一份 Compose。数据库、Redis、MinIO、应用端口、密码都从 `.env` 读取。JDBC 主机保持服务名 `mysql`。开发机和 Linux 用同一份文件，只允许 `.env` 里的端口和密码不同。服务器上同一套命令启动后，页面、登录、入库完成、出库完成、附件下载都可用。

周二下课前冻结功能。之后只修部署和缺陷，不加新接口。
